# asterx_driver 运行逻辑详解

> 本文对应代码版本：2026-07-28
> 入口文件：根 `main.cpp`（统一入口）→ `asterx_driver/src/asterx_driver_app.cpp`（本驱动入口）
>
> 硬件：Septentrio AsteRx-i3 D Pro+ —— 一台 GNSS/INS 组合导航接收机：双天线（主天线定位、
> 副天线 Aux1 与主天线构成基线解算航向）、内置 IMU（惯性测量单元，输出加速度/角速度）。
> 驱动通过以太网单条 TCP 连接与它对话，把原始 SBF 二进制流录到磁盘。

## 1. 统一框架背景（三驱动共享）

所有驱动都实现 `Common::IDriverApp`（`common/include/driver_app.h:21`），契约写在文件头注释
（`common/include/driver_app.h:4-11`）：

1. **init(external_stop)**：主线程按创建顺序逐个调用（`main.cpp:214-225`），负责把设备带起来；
   耗时的 bring-up 必须轮询 `external_stop`，这样 Ctrl+C 能中断初始化。
2. **run()**：每个驱动一个专属线程（`main.cpp:229-241`），阻塞到 `TerminateFlag()` 置位。
3. 主线程随后进入监视循环（`main.cpp:248-257`）：**任一**驱动的 TerminateFlag 置位、或收到
   信号（SIGINT 等，`main.cpp:84`），就把 terminate 传播给**全体**驱动（`main.cpp:263-265`），
   join 所有 run 线程（`main.cpp:273-277`），最后**逆序**调用 shutdown()（`main.cpp:278-280`）。

日志是单 spdlog 实例（`Common::Logger::init`，`main.cpp:74` 建立：stderr 只出 info 及以上，
会话文件记到 trace）。驱动内部日志与 lms4xxx/ins401 同款 —— 每个 .cpp 的匿名命名空间
一个 `Common::DriverLog g_log{ "AsteRx" }` 实例（如 `src/session.cpp:9-10`），默认放行全部
级别，由 sink 分级：控制台只显示 info+，会话文件完整落盘 trace+（命令审计因此总在文件里）；
而**生命周期 marker 行**直接走 `Common::Log`，
用 App 级 token `"AsterxApp"`（`common/include/driver_markers.h:23`），例如
`"AsteRx driver initialized (receiver configured, recording)"`（`driver_markers.h:30`）——
Web GUI 的健康状态机就是靠匹配这些字符串判断驱动活没活着，所以**这些行的措辞是红线**。

数据统一落 `<Output Directory>/<时间戳>/bin/asterx/`（覆盖逻辑在
`src/asterx_driver_app.cpp:103`）。

## 2. 启动与初始化（时间线）

### 2.1 构造：什么都不做

`AsterxDriverApp` 构造函数（`src/asterx_driver_app.cpp:25-30`）只拼出两个路径：驱动 YAML 的
绝对路径（exe 目录 + `../../` + `config-main.yaml` 里的相对路径）和会话数据目录。真正的加载
推迟到 init() —— 这样构造永不失败，统一 main 可以先把所有 DriverSlot 建好再逐个 init。

### 2.2 init()：加载配置 → 拉起 Qt 线程 → 等握手

`init()`（`src/asterx_driver_app.cpp:92-143`）在**主线程**执行，分四步：

1. **加载并校验 YAML**（`:96`，实现在 `src/app_config.cpp:109-184`）。校验很严：
   `rotate_bytes` 必须 >0 且 <2GiB（`app_config.cpp:163-167`，原因见 §5.1）；每条 stream 的
   区间 token、IMU 朝向模式、杆臂范围都在 `commands.cpp:329-363`（`validate_receiver_settings`）
   预检 —— **宁可在连接接收机之前就报错**，也不要发一半命令才发现配置非法。
2. **覆盖输出目录**为统一会话目录（`:103`）。
3. **启动 Qt 工作线程**（`:109`）—— 整个 Qt 世界（QCoreApplication、Session、SsnRx、四个
   QTimer）都关在这个线程里，主线程从不触碰任何 QObject（原因见 §8 问 1）。
4. **阻塞等 bring-up 握手**（`:111-119`）：一个三态原子协议 `Pending→Recording|Failed`
   （`include/asterx_driver_app.h:41`）。Qt 线程里 Session 首次进入 Recording 时发
   `configured` 信号 → `NotifyBringUp(Recording)`（`:58-59`）；致命失败发 `fatalError` →
   `NotifyBringUp(Failed)`（`:60-67`）。`NotifyBringUp`（`:38-44`）**第一个结果获胜**：
   之后的通知都是空操作，避免"先成功后失败"把 init 的判断搅乱。等待循环每 100ms 醒一次
   检查 `terminate_` 和 `external_stop`，所以 Ctrl+C 能打断还没连上接收机的 bring-up。

三种收场（`:121-142`）：Recording → 打 marker、返回 true；Failed → join Qt 线程、记错、返回
false（统一 main 会终止整个进程，`main.cpp:222`）；仍 Pending（外部打断）→ 置 terminate_
（Qt 线程里的 stop-poll 定时器看到后会执行 `Session::shutdown()` 中止 bring-up）、join、返回 false。

### 2.3 QtThreadMain：Qt 世界的全部

`QtThreadMain`（`src/asterx_driver_app.cpp:47-89`）：

- 每进程**至多一个** `QCoreApplication`（`:48-53`，argc/argv 是 static —— Qt 会长期持有引用）。
- 栈上构造 `Session`（`:56`，构造抛异常 = 输出目录建不了，直接走 catch → Failed）。
- 一个 100ms 的 **stop-poll QTimer**（`:71-78`）把外部的 `terminate_` 原子标志翻译成 Qt 世界
  的有序退出：`session.shutdown()` + `app.quit()`。这是**唯一**的跨线程控制通道 ——
  原子标志 + 轮询，绝不跨线程调 QObject 方法。
- `session.start(); app.exec();`（`:80-81`）—— 之后整个驱动的生命都在事件循环回调里度过。
- 退出路径上（`:87-88`）无条件再发一次 `NotifyBringUp(Failed)`（若仍 Pending）并置
  `terminate_`，保证 init()/run() 无论如何都会被唤醒。注意 `:89` 的注释：`~Session` 必须
  先于 `~QCoreApplication` 跑（栈序天然保证）—— Qt 的硬性要求。

### 2.4 Session 状态机：Connecting → WaitingDescriptor → Configuring → Recording

状态枚举在 `include/session.hpp:53-61`，整体策略写在类注释（`session.hpp:19-28`）。
四个 QTimer（`session.hpp:102-105`）各司其职，常量在 `src/session.cpp:9-12`：

| 定时器 | 周期 | 作用 |
|---|---|---|
| retry_timer_ | 5s 单发 | Backoff → 重新 Connecting |
| watchdog_timer_ | 30s 单发 | 每个 SBF 块重置；超时 = 链路活着但没数据 → 重连 |
| command_timer_ | 15s 单发 | 每条配置命令一发；没回复 → 失败处理 |
| stats_timer_ | 5s 周期 | Recording 态打一行统计日志 |

流程（都是 `SsnRx` 信号驱动的回调，接线在 `src/session.cpp:48-100`）：

1. **start_connect_**（`session.cpp:109-125`）：置 Connecting，**新建一个 SsnRx**（`:117-121`，
   为什么每次都新建见 §8 问 2），`connectTcp` 到 `<host>:28784`。
2. **TCP 连上**（`session.cpp:49-55`）：置 WaitingDescriptor，启动 15s 命令定时器，调
   `sendPromptRequest()`。SDK 先发一个回车（`ssnrx.cpp:568`），若超时再发 `"SSSSSSSSSS"`
   强制接收机进入命令模式（`ssnrx.cpp:576`）—— 接收机会回一个**提示符**（prompt，形如
   `IP10>`，正则在 `ssnrx.cpp:639`）。提示符去掉 `>` 就是**连接描述符**（connection
   descriptor）：接收机给本条 TCP 连接起的名字，后面所有 `setSBFOutput` 都精确瞄准它。
3. **拿到描述符**（`session.cpp:57-73`）：用它构建完整命令表（`build_command_list`），置
   Configuring，开始逐条发送。
4. **逐条命令**（`send_current_command_`，`session.cpp:128-138`）：发一条、起 15s 定时器、
   等 `newCommandReply` 回调（`handle_command_reply_`，`session.cpp:141-204`）；成功则发
   下一条，全部发完进入 `enter_recording_`（`session.cpp:207-215`）：置 Recording、置
   `ever_configured_ = true`（这个布尔决定以后失败是重连还是致命，见 §6）、启动 30s
   watchdog、发 `configured` 信号解锁 init()。

### 2.5 完整命令序列（commands.cpp）

`build_command_list`（`src/commands.cpp:159-243`）产出约 33 条 ASCII 命令，纯字符串逻辑、
可单测。顺序即依赖关系：

1. **login**（`:168-171`）：认证。日志里永远打码（`redact_cmd`，`:365-370`）。
2. **getReceiverCapabilities**（`:174`）：回复在 `session.cpp:162-172` 解析
   （`parse_receiver_capabilities_reply`，`commands.cpp:245-262`）；若配置要求双天线
   （`require_aux1: true`）而硬件没有 Aux1，**立即失败** —— 缺副天线意味着整个采集目的
   （GNSS 航向）不成立，录了也白录。
3. **清空全部十条 SBF 输出流**（`:179-185`）：`setSBFOutput, StreamN, none, none, off` × 10。
   接收机的流配置是**持久化**的 —— 上一次 RxControl 调试残留的流会悄悄复活、重复输出同一
   历元。回复"未配置"属正常，所以这十条标记为 `ToleratedError`（`commands.hpp:87`）：
   错误回复只记 debug 不算失败（`session.cpp:150-152`）。
4. **setDataInOut, <descriptor>, , +SBF**（`:189`）：在**我们自己这条连接**上打开 SBF 输出方向
   （中间留空 = 不动命令输入方向）。SBF（Septentrio Binary Format）是厂商的二进制块格式：
   每块 `$@` 同步头 + CRC + 块 ID + GPS 时戳 + 载荷。
5. **tracking 复位**（`:194-202`，可用 `tracking.enable_all: false` 跳过）：
   `setSatelliteTracking/setSignalTracking/setSignalUsage` 全开 + `setCN0Mask 0`。
   `setSignalTracking` 会**重启跟踪环路**，所以必须放在使能输出流之前 —— 否则刚开的流
   会先输出一段跟踪重启的残废数据。CN0 掩码设 0 = 弱信号原始观测也照录，筛选留给后处理。
6. **IMU 三件套 + 回读校验**（`:207-218`）：`setIMUStartupDataMode` →
   `setIMUOrientation`（IMU 安装朝向）→ **getIMUOrientation 回读**（`VerifyImuOrientation`，
   校验在 `commands.cpp:264-286`）→ `setINSAntLeverArm`（**杆臂**：IMU 参考点到主天线相位
   中心的三维向量，INS/GNSS 融合的几何基准）→ **getINSAntLeverArm 回读**（`:288-303`）。
7. **双天线姿态 + 回读**（`:221-234`）：`setGNSSAttitude, MultiAntenna` → 回读（`:305-314`）
   → `setAttitudeOffset`（天线基线与车体轴的夹角）→ 回读（`:316-327`）。
   为什么 set 完还要 get？—— 几何参数错了**不会报错**，只会让之后录的每一份数据都
   悄悄坏掉；回读比对（容差 0.001，`commands.cpp:56-58`）是唯一的保险。不一致 = 启动失败。
8. **7 条 setSBFOutput**（`:237-240`，命令拼装在 `build_sbf_output_command`，`:123-143`）：
   把配置里的 7 条流逐条压给接收机，目标都是本连接描述符。

每次重连后这套序列**原样重跑**（`commands.hpp:112-114`）—— 配置幂等，重跑无害，还能
修复接收机端被外部改动的状态。

## 3. 稳态数据流：一个字节从天线到磁盘

### 3.1 SDK 内分帧（厂商代码，未改动）

接收机把命令回复和 SBF 二进制**混在同一条 TCP 流**里发回来。socket 一有数据，
`SsnRx::onDataReceived`（`3rd_party/RxTools/ssnrx/src/ssnrx.cpp:371-382`）把字节追加进
内部缓冲 `mBuffer`，然后 `parse()`（`ssnrx.cpp:388-532`）循环扫描：见 `>` 按提示符处理、
见 `$R` 按命令回复处理（`$R?` = 错误回复，`ssnrx.cpp:661`）、见 `$@` 走
`parseSBF`（`ssnrx.cpp:809-855`）：

1. 校同步字 `$@`（`:814`）；
2. 读头部 length 字段（`:826`），不足 8 或没收全就等下一批字节；
3. 算 CRC 与头部比对（`:841-850`），错则发 `sbfCRCError` 并丢帧；
4. 通过则 `emit newSBFBlock(完整帧)`（`:852`）。

也就是说：**驱动拿到的每一个块都已经过同步/长度/CRC 三重校验**，Session 不需要再懂帧格式。
垃圾字节走 `discardedBytes` 信号，Session 只计数（`session.cpp:88-90`）。

### 3.2 on_sbf_block_：tee 点

`Session::on_sbf_block_`（`src/session.cpp:218-240`）是整个驱动的数据心脏，做四件事：

1. **门卫**（`:219-223`）：Backoff/Stopping 态直接丢弃 —— 保证 `.sbf` 分段边界与链路断口
   严格重合（一段文件内绝无"断线前后拼接"的数据）。
2. **写权威主路径**（`:224-232`）：`writer_.write_block(block)` 原样落盘。**写盘失败是
   录制器唯一不可幸存的错误**：critical 日志 → `shutdown()` → `emit fatalError()` →
   整个进程关停（磁盘满了还假装在录，比停下来更糟）。
3. **tee 到实时旁路**（`:235-236`）：`live_.on_block(...)`，noexcept，失败自我降级（§3.4）。
4. **喂狗**（`:237-239`）：重启 30s watchdog —— 只要块还在来，狗就不叫。

### 3.3 SbfWriter：轮转 .sbf（薄适配）

`SbfWriter`（`src/sbf_writer.cpp`）是 `Common::RotatingFileWriter` 的薄壳：

- 文件名 `<prefix>-<UTC紧凑时间戳>-<序号>.sbf`（`sbf_writer.cpp:16-21`，序号从 1 起）。
- 1 GiB 或 1 小时轮转（config），且 `precheck_size_cap = true`（`sbf_writer.cpp:24`）：
  写入**前**预判会不会超限，超了先轮转 —— `rotate_bytes` 是**硬上限**而非软阈值。
  这是 RxTools 契约：`sbf2rin/sbf2asc` 拒绝 ≥2GB 的输入文件（`app_config.cpp:163-167`
  的启动校验就是同一条红线的第一道闸）。轮转粒度是整块 —— SBF 块永不跨文件。
- `end_segment()`（`:42-48`）：断线时关闭当前段，重连后写新文件。

### 3.4 SbfLiveRecorder：实时 CSV 旁路（新增）

`.sbf` 是二进制，GUI 没法直接看。`SbfLiveRecorder`（`src/sbf_live_recorder.cpp`）在 tee 点
挑出**五种**块就地解析成物理单位、追加到五个 CSV（文件名与表头列契约硬编码在
`include/sbf_live_recorder.hpp:67-83`，Python 侧 `app/services/asterx_live.py:241-262`
按同一文件名与列名订阅所需的列子集——列名与表头对不上时告警并禁用该流）：

| 块 (ID) | CSV | 内容 |
|---|---|---|
| PVTGeodetic (4007) | live_pvtgeodetic.csv | 纯 GNSS 定位：经纬高、速度、精度 |
| ExtSensorMeas (4050) | live_extsensormeas.csv | 原始 IMU：加速度、角速度、温度 |
| INSNavGeod (4226/4230) | live_insnavgeod.csv | INS 融合解：位姿 + 航向俯仰横滚 + 标准差 |
| ReceiverStatus (4014) | live_receiverstatus.csv | 接收机自身：CPU、温度、错误位、AGC |
| AttEuler (5938) | live_atteuler.csv | 双天线 GNSS 姿态 |

`on_block`（`sbf_live_recorder.cpp:109-211`）先 `PeekId`（`src/sbf_parsers.cpp:119-124`，
只看头部 6 字节取 13 位块 ID），非五者之一直接 return（`:207-208`）—— MeasEpoch、星历等
只进 `.sbf`。解析器（`sbf_parsers.cpp`）是从 Septentrio ROS 驱动移植的纯函数，用
**先查边界后读**的 Reader（`sbf_parsers.cpp:40-100`）保证截断帧永不越界。

三个关键语义：

- **DNU → nan**：SBF 用哨兵值表示 Do-Not-Use（"此字段无效"）：浮点 `-2e10`、整型全 F
  （`include/sbf_types.hpp:54-64`）。浮点在读取时统一转 NaN（`sbf_parsers.cpp:81-94`），
  定标整型（如精度 0.01m 计）经 `scaled()` 转 NaN（`sbf_live_recorder.cpp:24-26`）——
  CSV 里写字面量 `nan`，Python 读回天然就是 NaN，不需要每列各记一个魔数。
- **GPS 周内秒 → Unix 时间**：SBF 时戳是 `tow`（GPS 周内毫秒）+ `wnc`（GPS 周计数）。
  `GpsToUnixNs`（`sbf_types.hpp:75-82`）换算：GPS 纪元 1980-01-06 = Unix 315964800s，
  加 `wnc` 周 + `tow` 毫秒，再减 18 闰秒（GPS 时不闰、UTC 闰，两者已漂 18s；常量
  `sbf_types.hpp:73`，IERS 宣布新闰秒时要手动 +1）。tow/wnc 是 DNU 时返回 0，每行同时
  带主机 Unix 时戳兜底（`sbf_live_recorder.cpp:16-21`）。
- **降级永不 fatal**：`append_`（`sbf_live_recorder.cpp:55-88`）里打开失败或写失败只把
  该通道 `failed = true`、记一次 error，**这个 CSV 从此闭嘴，其余四个和 .sbf 照常**。
  解析失败只递增计数（`:91-96`，第 1 次和每 1000 次记 warn）。整个 `on_block` noexcept。
  道理：旁路是"锦上添花"，它的任何故障都不配打断权威录制（对比 §3.2 第 2 条）。

CSV 每 0.5s 批量 flush 一次（`sbf_live_recorder.cpp:13`、`:99-106`）—— GUI tail 的节奏，
又不至于每行一次系统调用。文件**跨重连不换**（`sbf_live_recorder.hpp:42-44`）：GUI 看到的
是整个会话一条连续时间线，链路断口从数据缺口上自然可见。

### 3.5 为什么 PVT/INSNavGeod 单独一条 msec100 流

7 条流里前 6 条都是 `OnChange`（接收机自然更新率，不做驱动侧抽稀），唯独 Stream 7
（`config/config-asterx.yaml:86-92`）是 `msec100`：INS 融合解最高 200 Hz，`OnChange` 会让
CSV 旁路每小时膨出几百 MB 且 GUI 根本消化不了；`msec100` 把 PVTGeodetic + INSNavGeod 钳到
10 Hz —— 对 0.5s 的 GUI tail 绰绰有余，CSV 约 16 MB/h。而 IMU 原始数据（Stream 1）必须
全速率进 `.sbf`，所以不能把这两类塞进同一条流。

## 6. 错误与恢复

分水岭是 `ever_configured_`（`session.cpp:263-266`）：**首次配置成功之前**任何失败都是
致命的（`fail_startup_`，`session.cpp:282-290`：关停 + `fatalError` → 全进程退出）——
接收机不可达/密码错/几何回读不一致属于"人该来修"的问题，静默重试只会录出垃圾；
**首配成功之后**一切失败都走同一条恢复路（`handle_failure_`，`session.cpp:259-279`）：

```
断线 / 30s 无 SBF / 命令被拒 / 15s 无回复
    │
    ▼
handle_failure_：先置 Backoff（挡同步重入）→ 停两个定时器 → closeConnection()
    → writer_.end_segment()（关当前 .sbf 段）→ live_.flush()（CSV 不关）
    → retry_timer 5s
    │
    ▼ 5s 后
start_connect_：丢弃旧 SsnRx、new 一个 → 重连 → 重跑全部 33 条命令 → 新 .sbf 段
```

细节与动机：

- **先置 Backoff 再关 socket**（`session.cpp:268-274`）：`closeConnection()` 可能**同步**
  再发一次 `connectionClosed`（`ssnrx.cpp:108-112`），而该信号接的就是 `handle_failure_`
  （`session.cpp:97-99`）—— 若不先换状态，就会重入并把 retry 定时器重排一遍。函数入口的
  状态门卫（`:260-262`）吸收这次重入。
- **watchdog 30s**（`session.cpp:293-299`，常量 `:10`）：TCP 活着不代表数据在流 ——
  有人用 RxControl 连上去把流关了、或接收机僵死，socket 都不会断。30s 是"最慢的流也该
  来过好几个块"的保守值；每个块喂一次狗（`:237-239`），静默即视同链路失败走重连
  （重连会重跑配置，恰好把被外部改掉的流配置修回来）。
- **可恢复的解析噪声不算失败**（`on_communication_error_`，`session.cpp:243-256`）：
  SDK 把"CRC 错""块长度非法"这类逐块诊断也从 `communicationError` 信号报出来，但此时
  socket 还开着 —— 它们只是计数器（丢一块 SBF 无所谓，后面还有），其余 communicationError
  （真正的 socket 错误）才走 `handle_failure_`。
- **磁盘写失败**（`session.cpp:226-231`）与启动失败一样致命：`fatalError` → wrapper 置
  `terminate_`（`asterx_driver_app.cpp:60-67`）→ 统一 main 关停全体驱动。

## 7. 关停（时间线）

任何一端触发（Ctrl+C / 别的驱动死了 / 本驱动 fatal）后统一收敛：

1. 统一 main 给所有驱动置 TerminateFlag（`main.cpp:263-265`）；asterx 的 `run()` 只是
   `WaitUntilTerminated`（`asterx_driver_app.cpp:146-151`，实现
   `common/include/thread_util.h:34-39`），醒来即返回，run 线程被 join。
2. 逆序 shutdown 到本驱动（`asterx_driver_app.cpp:154-167`）：置 `terminate_` → Qt 线程里
   的 stop-poll 定时器 100ms 内看到 → `session.shutdown()` + `app.quit()`
   （`asterx_driver_app.cpp:72-77`）→ join Qt 线程 → 打 `"AsteRx driver shutdown
   completely"` marker（`driver_markers.h:31`）。
3. `Session::shutdown()`（`session.cpp:328-347`）幂等：置 Stopping、停四个定时器、
   `closeConnection()`（**关连接即停流** —— SBF 输出瞄准的是本连接描述符，连接一死流
   自动消失，接收机上不留垃圾状态）、关 `.sbf`、关 CSV、打最终统计行。
4. `QtThreadMain` 尾部 `session.shutdown()` 再跑一次也无害（`asterx_driver_app.cpp:82`，
   fatal 路径上早已 shutdown 过，这里是 quit 路径的 flush）。

## 8. 设计取舍问答

**问 1：为什么整个 Qt 世界要关在一个工作线程里？**
两个硬约束叠加：其一，厂商 SsnRx **不是线程安全的**，它的分帧缓冲、提示符状态机、命令队列
全都假设单线程访问，而它又是 QObject（信号槽依赖事件循环），所以它必须完整地活在某个
Qt 事件循环线程里；其二，**每进程至多一个 QCoreApplication**（`asterx_driver_app.cpp:48-49`），
而统一 main 的主线程要按序 init 五种驱动、不能被 `app.exec()` 独占。于是把
QCoreApplication + Session + SsnRx 整体塞进一个专属线程，跨线程只用原子标志 + 条件变量 +
join（`asterx_driver_app.h:7-8`），wrapper 永不触碰 QObject —— 没有跨线程信号槽的坑。

**问 2：为什么每次重连都要重建 SsnRx？**
SDK 的 `closeConnection()`（`ssnrx.cpp:78-113`）清了描述符、提示符、命令队列，**唯独不清
分帧缓冲 `mBuffer`**。断线往往发生在一个 SBF 块传了一半时 —— 残缺的半块躺在缓冲里，新连接
的字节接在它后面，轻则丢块、重则整段解析错位（`session.hpp:23-25` 称之为"缓冲中毒"）。
厂商代码约定不改（byte-identical vendoring），那就换个角度：SsnRx 便宜，重连时整个丢掉
new 一个（`session.cpp:117-121`），缓冲天然干净。注意丢之前要先 `rx_->disconnect(this)`：
它的析构会发 `connectionClosed`，不解绑会再触发一次失败处理。

**问 3：`.sbf` 为什么必须小于 2 GiB？**
不是文件系统限制，是**下游工具链契约**：RxTools 的 `sbf2rin/sbf2asc` 拒绝 ≥2GB 的输入。
与其让用户录完 8 小时才发现转不了，不如把轮转（1 GiB 硬上限 + 写前预检，
`sbf_writer.cpp:24`）当作后处理保证，并在配置加载时就拒绝非法值（`app_config.cpp:163-167`）
—— 同一条红线设三道闸：配置校验、预检轮转、postprocess.sh 里的尺寸复核。

**问 4：实时 CSV 失败为什么只降级、不重试也不报警升级？**
职责分层：`.sbf` 是**权威**（丢一字节都是事故，所以写失败直接 fatal），CSV 是**旁路**
（GUI 观赏用，事后可从 `.sbf` 完整重建）。旁路若有权打断主路径，就等于给次要功能发了
杀死主功能的许可证。所以 `on_block` 整体 noexcept，单通道失败单通道闭嘴
（`sbf_live_recorder.cpp:55-88`），连重试都不做 —— 磁盘型故障重试大概率还是失败，
反而在热路径上反复抖动。

**问 5：为什么命令和 SBF 数据共用一条 TCP，而不是分成命令口 + 数据口？**
把 SBF 输出瞄准**自己的连接描述符**（`commands.hpp:102-104`）换来一个极简的失效模型：
连接死 → 流死，接收机上永远不会留下一个"没人听却还在跑"的孤儿流；重连 = 重配，只有
一条恢复路径。双口方案则要处理"命令口活着数据口死了"等 2×2 组合，还得记得清理另一口
的流配置。代价（命令回复与二进制混流）由 SDK 的分帧器承担，驱动无感。

**问 6：几何参数为什么 set 之后还要 get 回读？**
杆臂、IMU 朝向、姿态偏置错了，接收机**照常工作**，INS 解照出 —— 只是系统性地错。这类
错误在数据里几乎不可见，等发现时几周的数据已废。回读校验（`commands.cpp:264-327`）把
"配置没生效/被固件悄悄改写/格式化丢精度"变成启动即失败，是全驱动性价比最高的十几行代码。

**问 7：为什么 bring-up 用"第一个结果获胜"的握手，而不是简单等 configured？**
Qt 线程可能在 init() 等待期间以任意顺序发生：先配置成功后磁盘 fatal、直接 fatal、
或外部 Ctrl+C。`NotifyBringUp`（`asterx_driver_app.cpp:38-44`）把三方竞争折叠成一次性的
三态原子结论，且约定 **outcome 先于 terminate_ 发布**（`:62-64` 注释）—— 否则 init() 可能
先看到 terminate_、把内部 fatal 误判成外部打断，走错收场路径。

**问 8：重连为什么固定 5s 退避，不做指数退避？**
对端是**局域网内的专用接收机**（`session.cpp:9` 注释），不是公网服务：不存在"雪崩时保护
服务器"的诉求，故障要么秒级恢复（网线松动）要么等人来修（断电）。指数退避只会在后者
场景把恢复延迟越拖越长，5s 恒定既不刷屏日志，又保证插回网线后最多 5s 恢复录制。
